# trending-service — виджет «Сейчас ищут»

Сервис агрегирует поток поисковых событий из Kafka и отдаёт **Топ-N** популярных запросов за последние **5 минут** через быстрый HTTP/JSON API.

## Быстрый старт

### Docker Compose

```bash
docker compose up --build -d
```

Поднимаются Zookeeper, Kafka (`confluentinc/cp-kafka:7.3.2`) и сервис на `:8080`.

### Отправка тестовых событий

```bash
go run ./cmd/producer -query "iphone 15" -count 5 -session user-1
go run ./cmd/producer -query "samsung s24" -count 3 -session user-2
```

### Примеры запросов к API

**Топ-10 (по умолчанию):**

```bash
curl -s http://localhost:8080/api/v1/top | jq
```

**Топ-5:**

```bash
curl -s "http://localhost:8080/api/v1/top?n=5" | jq
```

**Healthcheck:**

```bash
curl -s http://localhost:8080/healthz
```

**Стоп-лист — добавить слово:**

```bash
curl -s -X POST http://localhost:8080/api/v1/stoplist \
  -H "Content-Type: application/json" \
  -d '{"word":"конкурент"}' | jq
```

**Стоп-лист — удалить слово:**

```bash
curl -s -X DELETE "http://localhost:8080/api/v1/stoplist?word=конкурент" | jq
```

**Стоп-лист — список:**

```bash
curl -s http://localhost:8080/api/v1/stoplist | jq
```

Пример ответа `GET /api/v1/top`:

```json
{
  "window_seconds": 300,
  "generated_at": "2026-05-26T12:00:00Z",
  "items": [
    {"query": "iphone 15", "count": 42},
    {"query": "samsung s24", "count": 31}
  ]
}
```

## Контракт данных (Kafka)

**Топик:** `search.events` (env: `KAFKA_TOPIC`)  
**Ключ партиции:** `session_id` — равномерное распределение и упорядоченность событий одной сессии.

```json
{
  "query": "iphone 15",
  "timestamp": "2026-05-26T11:55:00Z",
  "session_id": "7b3c9f1a2e"
}
```

| Поле | Зачем нужно |
|------|-------------|
| `query` | Текст запроса для агрегации |
| `timestamp` | Привязка к 5-минутному окну |
| `session_id` | Лимит повторных поисков одной сессии в счётчике |

**Нормализация на стороне сервиса:** trim, lowercase, схлопывание повторяющихся пробелов.

## Архитектура

```
Kafka → Consumer → Aggregator (in-memory) ← HTTP handlers
                      ↑
                 Stoplist (in-memory)
```

### Хранение топа

- **Скользящее окно** из `BUCKET_COUNT` (по умолчанию 30) временных бакетов.
- Длительность бакета = `WindowDuration / BucketCount` (~10 сек при окне 5 мин).
- Каждый бакет: `map[query]count` + `map[query]map[session]hits` для лимита повторов.
- **Read path:** предвычисленный кеш топа (`TOP_CACHE_REFRESH`, default 1s) + heap Top-N при промахе.
- **Write path:** O(1) insert в текущий бакет.

### Стоп-лист

- In-memory `map[string]struct{}` под `sync.RWMutex`.
- Проверка при записи и при чтении топа (на случай добавления слова после записи).
- Подстроковое совпадение — компромисс для маркетинга (скрыть «конкурент» в любом запросе).

## Trade-offs и неясности в постановке

### Почему без БД

- Чтений в 10–50× больше записей → узкое место — GET `/api/v1/top`.
- Данные ephemeral (5 минут), потеря при рестарте допустима по постановке («по умолчанию нет данных»).
- In-memory + кеш даёт стабильную latency на порядок ниже disk/network round-trip.

### «В реальном времени», но без точных цифр

**Проблема:** не сказано, насколько свежим должен быть топ (100 мс? 5 сек?).

**Решение:** топ пересчитывается в фоне раз в секунду и отдаётся из кеша; в ответе HTTP стоит `Cache-Control: max-age=1`.

**Минус:** виджет может отставать от потока событий примерно на 1 секунду. Для главной страницы это обычно приемлемо, зато ручка `/api/v1/top` выдерживает очень высокую нагрузку на чтение.

### Стоимость пересчёта кеша при высокой кардинальности

**Проблема:** число уникальных запросов в 5‑минутном окне может быть очень большим (десятки/сотни тысяч). Полный пересчёт топа требует пройти по всем бакетам и по всем ключам в `map`.

**Решение:** мы пересчитываем топ фиксированно раз в `TOP_CACHE_REFRESH` (по умолчанию 1 сек), чтобы разгрузить `GET /api/v1/top` при высоком RPS на чтение.

**Минус:** CPU/аллоцкации пересчёта растут вместе с числом уникальных запросов. Если кардинальность высокая, интервал `TOP_CACHE_REFRESH` придётся увеличивать или переходить на прибавление нового бакета и вычитание старого, чтобы не пересчитывать всё окно каждый раз.

### Накрутка одним и тем же запросом

**Проблема:** бот может тысячи раз отправить один запрос и «взломать» топ.

**Решение:** одна сессия (`session_id`) может добавить не больше 3 засчитанных поисков по одному запросу в каждом коротком интервале (~10 сек). Настраивается через `MAX_HITS_PER_ACTOR`.

**Минус:** если реальный пользователь очень часто ищет одно и то же подряд, часть его поисков не попадёт в счётчик.

### Стоп-лист без правил

**Проблема:** не описано, как именно скрывать слова — только точное совпадение или «если слово встречается внутри запроса».

**Решение:** если стоп-слово есть в тексте запроса как подстрока, запрос не показывается (например, стоп-слово `конкурент` скроет и `конкурент x5`).

**Минус:** возможны ложные срабатывания, если стоп-слово случайно совпало с частью нормального запроса.

### Окно «5 минут» и опоздавшие события

**Проблема:** событие может прийти в Kafka с задержкой или с «чужими» часами.

**Решение:** учитываем `timestamp` из сообщения; если событие старше 5 минут — не считаем.

**Минус:** опоздавшее, но ещё актуальное по смыслу событие может быть отброшено.

### Конфигурация (env)

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `KAFKA_BROKERS` | `localhost:9092` | Брокеры Kafka |
| `KAFKA_TOPIC` | `search.events` | Топик с событиями поиска |
| `KAFKA_GROUP_ID` | `trending-service` | Consumer group |
| `BUCKET_COUNT` | `30` | Число бакетов в скользящем окне |
| `MAX_HITS_PER_ACTOR` | `3` | Лимит поисков одной сессии на один запрос в бакете |
| `TOP_CACHE_REFRESH` | `1s` | Как часто обновлять кеш топа |
| `DEFAULT_TOP_N` | `10` | N по умолчанию для `/api/v1/top` |
| `MAX_TOP_N` | `100` | Максимальное N в запросе |
